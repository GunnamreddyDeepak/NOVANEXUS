# BUSSENSE V2 — API Contract

## 1. Purpose

The BUSSENSE API provides the communication interface between the Edge Gateway and the Central Platform, and between the Central Platform and the GIS Control Tower.

The API is versioned to prevent uncontrolled breaking changes.

Base path:

/api/v1/

---

# 2. Architecture

The communication flow is:

EDGE GATEWAY
      ↓
CENTRAL API
      ↓
EVENT STORE
      ↓
FUSION / ANALYTICS
      ↓
GIS CONTROL TOWER

The Frontend must communicate with the Backend through APIs.

The Frontend must never directly access the database.

---

# 3. API Design Principles

1. APIs use JSON unless otherwise specified.
2. APIs use /api/v1/ versioning.
3. Event IDs are globally unique.
4. Event creation must be idempotent.
5. Backend validates all incoming data.
6. Authentication will be introduced for device communication.
7. Errors must use meaningful HTTP status codes.
8. API contracts must not be changed independently by individual team members.
9. Internal implementation may change without changing the external API contract.
10. Continuous raw video upload is not part of the API MVP.

---

# 4. Event APIs

## 4.1 Create Event

Method:

POST

Endpoint:

/api/v1/events

Purpose:

Submit an event generated by an Edge Gateway.

Request body:

The request body must follow EVENT_CONTRACT.md.

Example:

{
  "event_id": "EVT-ROAD-000001",
  "event_type": "ROAD_DAMAGE",
  "sub_type": "POTHOLE",
  "confidence": 87.4,
  "severity": "HIGH",
  "bus_id": "BUS-101",
  "device_id": "EDGE-101",
  "latitude": 13.0821,
  "longitude": 80.2691,
  "timestamp": "2026-09-09T18:30:00Z",
  "source_type": "REAL_EDGE_AI",
  "status": "VALIDATED",
  "evidence": {
    "image": "evidence/EVT-ROAD-000001.jpg"
  },
  "metadata": {}
}

Expected successful response:

HTTP 201 Created

Example:

{
  "success": true,
  "event_id": "EVT-ROAD-000001",
  "status": "CREATED"
}

If the same event_id is received again because of a retry, the backend must not create a duplicate event.

# 5. Get Events

Method:

GET

Endpoint:

/api/v1/events

Purpose:

Retrieve urban events for the control tower.

Supported query parameters may include:

event_type
severity
status
bus_id
source_type
start_time
end_time
latitude
longitude
radius

Example:

/api/v1/events?event_type=ROAD_DAMAGE&severity=HIGH

Response:

{
  "success": true,
  "events": []
}

---

# 6. Get Single Event

Method:

GET

Endpoint:

/api/v1/events/{event_id}

Purpose:

Retrieve complete information for one event.

Example:

/api/v1/events/EVT-ROAD-000001

Response:

{
  "success": true,
  "event": {}
}

If the event does not exist:

HTTP 404 Not Found

---

# 7. Event Status Update

Method:

PATCH

Endpoint:

/api/v1/events/{event_id}/status

Purpose:

Update the operational status of an event.

Allowed status values:

DETECTED
VALIDATED
FUSED
CONFIRMED
ACKNOWLEDGED
RESOLVED

Request:

{
  "status": "ACKNOWLEDGED"
}

Response:

{
  "success": true,
  "event_id": "EVT-ROAD-000001",
  "status": "ACKNOWLEDGED"
}

# 12. Fusion Request

The Fusion Engine receives validated events from the central event store.

Fusion should consider:

- Event type
- Subtype
- Spatial proximity
- Time window
- Different bus IDs
- Confidence
- Observation consistency

The API must not treat repeated detections from the same bus as automatic multi-bus confirmation.

# 13. Analytics API

Method:

GET

Endpoint:

/api/v1/analytics

Purpose:

Retrieve aggregated urban intelligence.

Initial analytics include:

- Vehicle density
- Congestion hotspots
- Road damage hotspots
- Repeated hazards
- Road health
- Waterlogging hotspots
- Infrastructure deficiency concentration
- Route delay indicators

Possible query parameters:

event_type
route_id
start_time
end_time
latitude
longitude
radius

Example response:

{
  "success": true,
  "analytics": {
    "total_events": 0,
    "congestion_hotspots": [],
    "road_damage_hotspots": [],
    "road_health": []
  }
}

# 14. Evidence API

Evidence files must be associated with an event.

## 14.1 Upload Evidence

Method:

POST

Endpoint:

/api/v1/evidence

Content type:

multipart/form-data

The upload should contain:

- event_id
- evidence file
- evidence type

Example evidence types:

IMAGE
VIDEO_CLIP

The system should prefer small event-specific evidence rather than continuous video.

---

# 15. Get Evidence

Method:

GET

Endpoint:

/api/v1/evidence/{event_id}

Purpose:

Retrieve evidence associated with an event.

Access to evidence must eventually require authorization.

# 17. Gateway Synchronization

The Edge Gateway must support offline synchronization.

Flow:

Event generated
      ↓
POST /api/v1/events
      ↓
Success?
   ↙       ↘
 YES        NO
 ↓          ↓
Delivered  Local Queue
             ↓
       Retry after network recovery
             ↓
       POST original event
